## 本次迁移的设计说明（手机号加密，方案 C）

| 项 | 做法 |
|---|---|
| 密文 | `encrypt_rand()` 随机 IV —— 相同号码每次密文都不同，抗枚举对照 |
| 索引 | `phone1_idx` = HMAC-SHA256(规范化号码)，密钥由主密钥**派生**（`_get_index_key`），索引泄露也推不出加密密钥 |
| 规范化 | `normalize_phone()` 去掉 `+86`、横线、空格 —— `138-0000-0000` 与 `13800000000` 能互相查到 |
| 精确查询 | `filter_by(phone1_idx=Student.phone_index(号码))` |
| 模糊查询 | 解密候选集后内存过滤（全校 2114 人，毫秒级） |
| 读取 | 模型 property 透明解密，页面/导出/导入业务代码无感 |
| **不能**再用 | `Student.phone1.like(...)`、`filter_by(phone1=...)` —— property 不能用于 SQL |

### 配套改动（必须一起，否则会出错）

1. **`app/utils/crypto.py`**：新增 `blind_index()` / `normalize_phone()` / `_get_index_key()`；
   `decrypt()` 兼容 11 位明文（迁移前的存量数据）。
2. **`app/utils/trash.py`**：归档/恢复改用 **mapper 属性 key**（`__mapper__.get_property_by_column(col).key`），
   不能用 `col.name` —— 否则归档时 property 会把密文解密成明文写进 `trash_records.payload`，
   恢复时 setter 又会**二次加密**。
3. **回收站 payload 现在存的是密文**：身份证、手机号在回收站里都是密文形态，恢复按属性 key 直写，不解密。
4. **登录名不受影响**：`users.username` 仍是可读的账号标识，登录链路没动。

## 关联改动：毕业生表与校友站（2026-10-19）

| 位置 | 处理 |
|---|---|
| `history.db` → `graduated_students` | **新归档自动是密文**（归档从 `students` 搬运，源已是密文）；**历史明文不回迁**——`decrypt()` 兼容 11 位明文，读取处统一解密后交给模板脱敏，显示与查询都不受影响 |
| `grade_mgmt.py` 历史页 / 校友页（2 处） | 读取时对 `phone1`/`phone2` 先 `decrypt()` 再渲染（此前身份证做了这步、手机号漏了） |
| `alumni_app` 校友站 | 与身份证同口径：解密 → 掩码 → `pop` 明文，模板改渲染 `phone1_masked` / `phone2_masked`；新增 `mask_phone`（与主站同口径 `139****1234`） |

**为什么历史明文不回迁**：毕业生表是只读快照、量小且已归档，回迁收益低；而 `decrypt()` 对明文直接返回，读写两侧都天然兼容，不回迁也能正常显示与脱敏。
