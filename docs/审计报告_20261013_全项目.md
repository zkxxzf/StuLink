## 5. 域三：性能（30 条，重点摘录）

> 说明：性能子代理无 shell 权限，量化为基于数据规模（2114 学生 / 21 场考试 / exam_scores 约 25–44 万行）的估算；关键 SQL 建议按报告附录脚本用 `EXPLAIN QUERY PLAN` 实测确认。

### 高风险（6）

| ID | 问题 | 位置 | 估算影响 |
|---|---|---|---|
| PERF-01 | 成绩落库 `_refresh_snapshot` 每名学生全量遍历 `existing`（2.1 万条）×2 次，其中一次 `skip_deleted=True` 为**纯空转** | `grades/services/store_service.py:61,96,145-159` | 导入一次多花 4–7s 纯 CPU，且在写事务内持锁 |

| PERF-25 | 非 WAL（delete 模式）下 SQLite 锁为**库级**：任一写事务阻塞该库全部读；busy_timeout 仅 5s | `app/__init__.py:36-40`、`config.py:84-95` | 架构级约束，16 线程反而加剧锁排队 |
| PERF-03 | 批量调课循环内按 `original_entry_id` 查重，该列**无索引** → 每行全表扫描 schedule_swaps（260 行统一调课 = 260 次全扫） | `academic/services/swap_service.py:870,2111`；模型索引 `models/timetable.py:442-445` | 0.5–20s |
| PERF-06 | `/grades/api/options` 无 WHERE 全表 `DISTINCT` exam_scores（分析页首屏第一请求，无缓存） | `grades/routes/analysis.py:140-142` | 每次 300–800ms |
| PERF-15 | 成绩仪表盘无缓存 + 前端 30s 轮询，含 3 条跨 25–44 万行的 `COUNT(DISTINCT)` | `grades/routes/dashboard.py:34-39`、`dashboard_service.py:73-98` | 100 人在线 = 每分钟 200 次重聚合，是 grades.db 最大读压力源 |

### 中风险（择要）

- **PERF-02** 未出现学生清理 O(n²)（`store_service.py:100-106`）；**PERF-04** 批量换课循环内每次 2–4 条查询（`swap_service.py:2128`）；**PERF-05** 教务工作台循环统计 + 全量加载 FormAnswer（`form_summary_service.py:328-367`）。
- **PERF-07** 操作日志页每次翻页 4 次全表 DISTINCT + `User.query.all()`（`operation_logs.py:59-68`）。
- **PERF-08** ExamData 单场 2.1 万 ORM 对象 ≈ 30–50MB，进程级常驻 3 场（90–150MB）；注释声称的"双重检查"实际未实现，冷启动 16 线程串行构建（`stats_service.py:34-63`）。
- **PERF-09/10** 全局对比与热力图逐班全量扫描 total_rows（可一次分组解决）。
- **PERF-14** `config.py:69-71` 的 `CACHE_TYPE/CACHE_DEFAULT_TIMEOUT` 是**死配置**（flask-caching 从未初始化，真实缓存在 `app/utils/cache.py:105`）——误导运维。
- **PERF-18** 缓存 maxsize=1024 被班级/教师 tab key 挤爆（单 21×40=840），LRU 抖动致命中率随人数下降；**PERF-19** 改一科分 → 21 场考试的 `grades_report_*` 缓存与全部 ExamData 全清（`grades/utils.py:90-100`）。
- **PERF-20** `echarts.min.js` 1005KB 在 15 个模板各自引入（有 immutable 缓存缓解，但版本更新后全站重拉 1MB）。
- **PERF-26** 排名重算单事务 2.1 万行 UPDATE（`ranking.py:35-91`）。
- **PERF-30** 全校总课表一次渲染 ~3250 格 / 1.5 万 DOM 节点 + sticky 冻结，滚动掉帧。
