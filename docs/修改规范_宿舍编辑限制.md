# 宿舍编辑限制修改规范 (Spec)

> 版本：v1.1 | 日期：2026-07-19 | 状态：已完成 ✅

---

## 问题描述

**现象1**：宿舍已分配给班级并安排床铺给学生后，通过单个房间编辑页面（`/rooms/<id>/edit`）仍可修改性别和床位数。

**现象2**：批量设置功能（`/rooms/batch-setting`）仍然可以修改已分配宿舍的性别。

**根因1**：`edit()` 函数未做已分配检查（已在 v1.0 修复）。

**根因2（关键）**：`run.py` 默认使用 **waitress（生产模式）**，**不会自动重载代码**。7/16 启动的 python 进程一直在运行旧代码，这 3 天来对 `rooms.py` 的所有修改都没生效。用户测试时后端实际运行的是旧逻辑。

**影响**：
- 修改性别会导致已分配的学生与宿舍性别不匹配
- 修改床位数会调用 `_adjust_beds` 可能删除已分配学生的床位
- 破坏数据一致性

---

## 修改方案

### 修改1：单个房间编辑限制（v1.0 已完成）

**文件**：`app/modules/dormitory/routes/rooms.py` 的 `edit()` 函数

**逻辑**：检查 `room.class_name` 和 `BedAssignment.student_id`，若已分配则拒绝修改性别和床位数。

### 修改2：批量设置限制（v1.0 已完成）

**文件**：`app/modules/dormitory/routes/rooms.py` 的 `batch_setting()` 函数

**逻辑**：同上，遇到已分配房间时全部回滚。

### 修改3：重启服务使代码生效（本次修复重点）

**操作**：
1. 杀掉 7/16 启动的旧 python 进程（waitress 模式，不自动重载）
2. 使用 `python run.py --dev` 开发模式重启（Flask debug 模式自动重载）
3. 后续修改 .py 文件会自动生效

---

## 验证步骤

1. **重启服务后**，选择一间已分配班级且有学生入住的宿舍
2. 访问 `/rooms/<id>/edit`，尝试修改性别 → 应被拒绝，提示"已分配给班级..."
3. 尝试修改床位数 → 应被拒绝
4. 在 `/rooms/` 页面批量勾选已分配宿舍，尝试批量修改性别 → 应被拒绝，提示"X间宿舍无法修改"
5. 尝试修改备注 → 应允许（不触发限制）
6. 清除宿舍分配和床铺后，修改性别和床位数 → 应允许

---

## 风险与注意事项

- **开发模式仅限本地**：生产环境仍用 waitress，改代码后需手动重启
- **不限制备注等非关键字段**：用户仍可修改 notes、grade、class_name 等分配信息
- **向前兼容**：不改变 API 接口签名
- **与批量设置一致**：单个编辑和批量设置使用相同的检查逻辑
