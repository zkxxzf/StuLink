# 合班宿舍手动调整位置 — 方案对比规范

> 创建日期：2026-07-19
> 适用文件：`room_assignment_v4.py` + `assign_auto.html`
> 用户需求：在最后一步（执行分配前）允许手动调整合班宿舍位置

## 一、用户需求场景

```
算法分配结果：
  215: 2023级 05班 8人
  216: 2023级 05班 7人
  217: 2023级 06班 8人
  ...
  313: 合班(05班+06班) 6人  ← 用户想移到前面
  314: 合班(07班+08班) 6人

用户期望：
  215: 合班(05班+06班) 6人  ← 把合班放在班级中间
  216: 2023级 05班 8人      ← 原215学生
  217: 2023级 05班 7人      ← 原216学生
  ...
```

## 二、方案对比

### 方案A：连锁推挤（用户描述的方案）

**原理**：合班宿舍移到目标位置后，原目标房间的学生推到下一间，依次推挤，直到填满原合班宿舍空出的位置

**示例**：
```
原: 215(A班) → 216(A班) → 217(B班) → ... → 313(合班)
后: 215(合班) → 216(A班,原215) → 217(A班,原216) → ... → 313(A班,原312)
```

**优点**：
- 符合用户直观思维
- 保持班级顺序连续

**缺点**：
- ❌ **破坏班级房间数均衡**：推挤会导致某班房间数变化
- ❌ **可能违反强基班连续性**：推挤后强基班房间号可能不再连续
- ❌ **实现复杂**：需处理循环推挤、边界、容量变化
- ❌ **连锁影响大**：调整1间可能影响10+间房间
- ❌ **容量校验复杂**：6人间和8人间推挤时容量不匹配

**风险等级**：高 ⚠️

---

### 方案B：直接交换（推荐）⭐

**原理**：用户指定目标房间后，直接交换两个房间的分配内容

**示例**：
```
原: 215(A班8人) | 313(合班6人)
后: 215(合班6人) | 313(A班8人)
其他房间完全不变
```

**优点**：
- ✅ **实现简单**：只交换两个房间
- ✅ **不影响其他房间**：所有其他房间分配保持不变
- ✅ **不破坏班级连续性**：班级房间段不变，只是某间房变成合班
- ✅ **不违反硬约束**：强基班房间号不变
- ✅ **可多次调整**：用户可连续交换多次

**缺点**：
- ⚠️ 交换后 313 变成普通班房间，可能离班级段较远
- ⚠️ 合班宿舍容量可能不匹配（6人间vs8人间）

**风险等级**：低 ✓

---

### 方案C：拖拽交换（体验最好）

**原理**：在预览页面提供拖拽功能，用户拖拽合班宿舍到目标位置，自动交换

**优点**：
- ✅ 用户体验最好
- ✅ 可视化操作直观

**缺点**：
- ❌ **实现复杂度最高**：需引入拖拽库
- ❌ **移动端不友好**
- ❌ **测试工作量大**

**风险等级**：中

---

## 三、推荐方案：方案B（直接交换）

### 理由
1. **实现简单**：只交换两个房间的分配，不涉及连锁推挤
2. **风险低**：不影响其他房间分配，不破坏硬约束
3. **满足核心需求**：用户可以把合班宿舍放在班级中间
4. **可扩展**：未来可以在此基础上增加拖拽功能

### 容量不匹配处理

**场景**：合班宿舍313是6人间(6人)，目标房间215是8人间(8人)

**处理方式**：
- 交换后 215 变成合班宿舍(6人住8人间，空2个床位)
- 交换后 313 变成普通班宿舍(8人住6人间，**超容！**)

**解决方案**：
- ❌ 禁止容量不匹配的交换（6人间只能与6人间交换，8人间只能与8人间交换）
- ✅ **允许交换，但提示容量变化**：合班学生数 ≤ 目标房间容量，且原房间学生数 ≤ 合班房间容量

### 实施设计

#### 前端交互流程

1. **预览页面**显示合班宿舍列表（高亮标记）
2. 每个合班宿舍卡片旁有 **"↔ 交换位置"** 按钮
3. 点击后弹出 **房间选择器**：
   - 显示所有已分配的普通班房间
   - 标注每间房的容量和当前学生数
   - 用户选择目标房间
4. 系统提示确认：
   ```
   确认交换？
   - 房间 313 (合班: 05班+06班, 6人) ↔ 房间 215 (2023级 05班, 8人)
   - 交换后: 215=合班(6人/8人间), 313=2023级 05班(8人/6人间)
   ⚠️ 容量警告: 313房间容量6 < 学生数8，无法交换！
   ```
5. 校验通过后执行交换，更新预览

#### 容量校验规则

```python
def can_swap(room1_assign, room2_assign):
    """检查两个房间是否可以交换"""
    room1_cap = room1_assign['room'].capacity
    room2_cap = room2_assign['room'].capacity
    students1 = room1_assign['expected_count']
    students2 = room2_assign['expected_count']
    
    # 交换后：room1住students2，room2住students1
    if students2 > room1_cap:
        return False, f"房间{room1}容量{room1_cap} < 学生数{students2}"
    if students1 > room2_cap:
        return False, f"房间{room2}容量{room2_cap} < 学生数{students1}"
    return True, "可以交换"
```

#### 数据流

由于是 dry_run 预览阶段：
1. **前端直接交换**：JavaScript 修改 assignments 数组
2. **不需要后端 API**：所有交换在前端完成
3. **最终提交**：用户确认后，把交换后的 assignments 提交给后端执行
