# StuLink 性能测试报告 · 200 人同时使用（2026-10-15）

> 目标口径（用户规则）：接口响应 **P95 < 500ms**；冷计算单次 < 3s。
> 背景诉求：「匹配我们同时使用量 200 多人，去做性能测试」。

## 0. 结论摘要（TL;DR）

| 口径 | 说明 | 吞吐 | P50 | **P95** | P99 | 错误 | 服务端异常 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **① 真实节奏**（200 人在线，平均 30 秒一次操作） | 生产现有配置 | 5.9 req/s | 13ms | **194ms** | 503ms | **0** | 无 |
| ①′ 同上，生产原配置（16 线程/池 10/无 WAL） | 复测 | 5.7 req/s | 16ms | **242ms** | 499ms | **0** | 无 |
| **② 4 倍频率**（每人每 5.5 秒一次） | 生产原配置 | 34 req/s | 19ms | **388ms** | 648ms | **0** | 队列警告 117（峰值 9） |
| ③ 13 倍频率（每人每 1.5 秒一次，极限） | 生产原配置 | 66 req/s | 1035ms | 2910ms | 4229ms | 54×500 | locked 116 |
| ③′ 同上，WAL + 64 线程 + 池 40 | 推荐容量配置 | 69 req/s | 913ms | 2679ms | 6199ms | **0** | **locked 0** |

**结论三句话**：

1. **真实使用强度下（200 人同时在线、正常点页面的节奏），当前生产配置已经达标且有 ≥4 倍余量**
   （P95 242ms < 500ms，0 错误）。
2. **退化拐点在「每人每 5～10 秒一次操作」附近**：4 倍频率仍达标（P95 388ms），
   13 倍频率才出现排队与 5xx。
3. **若要为极端峰值（全员高频刷页 / 大量同时导出）兜底**：把 `SQLITE_ENABLE_WAL=1`
   （消除 100% 的 `database is locked` 与 5xx）+ 连接池提到与线程数同量级即可 ——
   已在对照组验证：5xx 由 54 → **0**、locked 由 116 → **0**。

## 1. 测试环境与方法

- **被测服务**：本地沙箱，**真实数据副本**（2114 学生 / 95 个账号 / 21 场考试 / 67898 条成绩 /
  2865 条课表条目），waitress 与生产同规格（默认 16 线程，可覆盖），多库 SQLite。
- **会话**：按真实角色分布（班主任 69 / 任课教师 23 / 管理员 2 / 年级长 1）为每个虚拟用户（VU）
  签发真实会话（`_user_id` + `_pwd_fp` + `_id` 三要素），**不绕开权限**：
  - probe 阶段先用各角色真实账号扫全部 **137 个无参页面**，按返回内容剔除"重定向到修改密码页"的假可用，
    得到**每个角色真实可访问的页面池**（班主任 52 / 教师 30 / 管理员 133 / 校长 62）；
  - 成绩分析 API **只有管理员可访问**（14/14；其余角色 403）—— 与生产权限配置一致，压测不越权。
- **负载模型**：每 VU 循环「页面 60% + 重计算 API 40%」，两类思考时间口径见下；
  管理员按 3% 概率发**幂等写**（查课标记同格覆盖，命中 SQLite 写锁路径）。
- **数据修正（重要）**：真实库里 93 个账号处于 `must_change_pwd=1`（首次登录必须先改密码），
  非 GET 请求会被 401 拦截。200 人在用 = 老师早已改过密码，故在**沙箱副本**上把该标记清零
  （只动副本，不动仓库 `data/` 与生产）。
- **服务端指标**：每档统计 waitress 队列警告（含峰值深度）、`database is locked`、Traceback 次数。
- 工具：`tests/_archive/qa_20261015/` 下 `prep_sandboxes.py`、`load_200.py`、`bench_matrix.py`、
  `profile_pages.py`；原始结果 JSON 在 `out/`。

> **测量学注意**：压测客户端与被测服务**同机运行**（开发机），极限档下二者争抢 CPU，
> 因此③类极限档的绝对延迟偏保守（真实服务器上应更好）。①②类真实/近真实档客户端开销可忽略，
> 数字可信。

## 2. 口径一：真实使用节奏（200 人在线）— 达标

场景：200 个并发用户同时在线，每人平均 **30 秒**操作一次（思考 15~45s 随机），持续 3 分钟。

| 指标 | 生产原配置（16 线程 / 池 10 / 无 WAL） | 容量配置（WAL / 64 线程 / 池 40） |
| --- | --- | --- |
| 请求数 | 1274 | 1305 |
| 实测吞吐 | 5.7 req/s | 5.9 req/s |
| P50 | 16ms | 13ms |
| **P95** | **242ms** ✅ | **194ms** ✅ |
| P99 | 499ms | 503ms |
| max | 793ms | 678ms |
| 真实错误（5xx/连接失败） | **0** | **0** |
| 权限拒绝 401/403 | 102（口径正常，不计错误） | 133（同） |
| 服务端队列警告 / locked | 0 / 0 | 0 / 0 |

**唯一超过 500ms 的端点**：`/statistics/export-bed-detail`（宿舍床铺明细 Excel，P50 553ms / max 793ms）
—— 属 Excel 生成开销（单请求无并发实测 431~444ms），用户点击导出等 0.5~0.8 秒可接受。

## 3. 口径二：4 倍操作频率（每人每 5.5 秒一次）— 仍达标

生产原配置，200 VU × 120s：

- 吞吐 34.0 req/s；**P50 19ms / P95 388ms / P99 648ms / max 1696ms**；**0 错误**

## 4. 口径三：极限频率（每人每 1.5 秒一次）与配置对照矩阵

200 VU × 60~120s，逐档改沙箱配置（`bench_matrix.py`）：

| 档位 | 线程 | 池 | WAL | 吞吐 | P50 | P95 | P99 | 5xx | 队列峰 | locked |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 16t-p10-base（＝生产现配置） | 16 | 10 | 否 | 66.2 | 1035 | 2910 | 4229 | 54 | 83 | 116 |
| 64t-p10（只加线程） | 64 | 10 | 否 | 34.8 | 1232 | **9136** | 19518 | **407** | 83 | **2255** |
| 64t-p40（线程+池） | 64 | 40 | 否 | 68.5 | 1031 | 2695 | 3618 | 49 | 83 | 105 |
| **64t-p40-wal（＋WAL）** | 64 | 40 | **是** | 68.6 | **913** | 2679 | 6199 | **0** | 83 | **0** |
| 32t-p20-wal | 32 | 20 | **是** | 62.9 | 1096 | 3725 | 6333 | **0** | 83 | **0** |

**读表要点**：

1. **`database is locked` 的根因是「非 WAL + 连接池过小」**：
   只加线程不加池（64t-p10）最差 —— 2255 次 locked、407 个 5xx（16 线程里挤 64 线程抢 10 个连接）。
2. **WAL 是消除 5xx 的决定因素**：两个 WAL 档 5xx 与 locked 全部为 **0**。
3. 极限档的 P50/P95 由**排队**主导（同档单请求实测仅 10~90ms），不是端点本身慢。
4. 队列深度峰值 83 在各种线程/池配置下相同 —— 说明瓶颈在**长耗时请求占住工作单元**
   （Excel 导出、宽表页面），而非配置本身；提升线程只改变排队位置，不改变长请求耗时。

## 6. 本次发现与已修

### 6.1 已修：宿舍「未分配住校生」统计（`_unassigned_stats`）

- 问题：`StudentAccommodation.query.all()` / `BedAssignment.query.all()` 加载**整表 ORM 对象**只为取
  `student_id`；随后拼 `Student.id.in_(2000+ ids)` 与 `~Student.id.in_(2000+ ids)` **巨型 IN/NOT IN**；
  最终取回整行 ORM 对象再分组。
- 改法（`app/modules/dormitory/routes/assignments.py`）：① `with_entities` 只取 id 列；
  ② 「已分配」判断移到 Python 集合差；③ 最终只取 `(id, grade, class_name, gender)` 四列。
  范围收敛仍在 SQL 侧走 `student_scope_query`（fail-closed 口径不变，第三轮审计 SEC-01 结论保持）。
- 效果：单请求中位 26~51ms（该页在 200 VU 极限档曾是 P50 5.2s 的贡献者之一）。

## 7. 生产建议

1. **当前无需改动即可支撑 200 人正常使用**（真实节奏 P95 242ms、0 错误）。
2. **若希望极端峰值也零错误**（例如成绩发布日大量老师同时刷分析页、集中导出）：
   - 在 `docker-compose.yml` 增加 `STULINK_ENABLE_WAL=1` 后重启（NAS 的 `stulink-data` 是
     容器卷、非同步盘，无 WAL 伴生文件风险；`history.db` 保持非 WAL 以满足 alumni 只读挂载）；
   - 同时把 `run.py` 的 `STULINK_THREADS` 与 `config.py` 的 `pool_size` **按同量级**调整
     （建议 32 线程 / pool 32）；**只加线程不加连接池会更差**（见 64t-p10 档）。
3. 若要进一步压低极限档延迟：优先优化 `export-bed-detail` 的 Excel 生成
   （openpyxl 逐格样式）与导出类端点的并发隔离 —— 它们是占住工作单元的长请求。

## 8. 局限与后续

- 客户端与服务端同机（极限档数字偏保守）；生产 NAS 上建议用同一脚本复测一次确认。
- 未覆盖：AI 分析（外部 API 依赖）、成绩导入（会持锁的长事务）、Excel 大批量导入。
  这三类属"长事务"场景，建议在**导入窗口**单独观察（导入期间的读延迟是下一个风险点，
  本轮已看到 `database is locked` 只在非 WAL 下出现）。
- 后续（点击测试环节）将继续核对 §6.2 的四个接口现象。
