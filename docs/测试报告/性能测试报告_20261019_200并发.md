# 性能压测报告 · 200 并发复测（2026-10-19）

> 目的：在数据导入页合并（成绩/划线/AI 同页）与侧栏调整后，复测
> 「200 人同时使用」与「200 个请求同时打过来」两条线，并单测新页面的并发。
> 环境：真实数据副本 + 生产同规格 waitress 16 线程、SQLite 多库、未开 WAL；
> 沙箱 `%TEMP%\stulink_sbx_a4`（端口 5099），
> 数据 2114 学生 / 31 场考试 / 108055 条成绩。
> 工具：`tests/_archive/qa_20261015/load_200.py`，本批脚本在
> `tests/_archive/qa_20261019/`，结果 JSON 在 `qa_20261015/out/`。

## 一、结论

| 场景 | 负载 | P50 | P95 | P99 | 5xx | 判定 |
|---|---|---|---|---|---|---|
| **真实使用**：200 人/30 秒一次 | 5.7 req/s | 19ms | **58ms** | 184ms | **0** | 达标 |
| 50 并发（每 1.5 秒一次） | 32.1 req/s | 20ms | **123ms** | 206ms | 0 | 达标 |
| 100 并发（每 1.5 秒一次） | 61.6 req/s | 28ms | **344ms** | 557ms | 0 | 达标 |
| **200 并发**（极限档） | 97.2 req/s | 425ms | **1106ms** | 1653ms | **0** | 变慢不崩 |

**一句话**：**真实使用余量充足（P95 58ms，只有目标的 1/8）**；
200 个请求同时打过来会排到 1.1 秒，但**没有 5xx、没有 `database is locked`**，
16 线程队列峰值 82，属于"变慢但不崩"。

> 首轮极限档（未剔除限流端点）出现 133 个 429 与 4 个 500：
> 429 全部来自故意限流的 `/qr/new`、`/wechat-bind/new`；
> 4 个 500 中 2 个 `/grades/api/options`、1 个
> `/grades/api/student-query/options`、1 个 `/wechat-bind/new`。
> 剔除两个限流端点后复测 **0 个 5xx**；首轮未抓服务端堆栈，
> 按 SQLite 写锁争用归因，作为极端峰值残余风险记录（见 §五）。

## 二、方法

- 角色分布按真实账号：班主任 145 / 任课教师 48 / 管理员 4 / 校长 2，
  共 199 个虚拟用户；同一账号可多 VU 复用（老师多设备）。
- 页面池先 probe（真实返回 200 的页面），按角色下发；
  本批剔除 `/qr/new`、`/wechat-bind/new` 两个**故意限流**的 AJAX 端点，
  避免把 429 当性能问题。
- 请求构成：页面 60% + 重计算 API 40%；管理员 3% 概率发幂等写
  （查课标记同格覆盖），测 SQLite 写锁争用。
- 真实节奏：思考 30 秒 + 每个 VU 启动错峰 0~30 秒（避免 200 个请求同一毫秒）。
- 极限档：思考 0.5~2.5 秒，即真实频率的 **20 倍**。

## 三、新页面专项

50 并发 × 1000 请求/端点（管理员会话，真实 HTTP）：

| 端点 | 状态 | P50 | P95 | max |
|---|---|---|---|---|
| `/grades/exams/34/import` | 1000×200 | 472ms | 559ms | 623ms |
| `/grades/exams/34/ai-import` | 1000×200 | 468ms | 559ms | 617ms |
| `/grades/exams/34/bands` | 1000×200 | 281ms | 339ms | 406ms |
| `/grades/exams/34`（考试详情，对照） | 1000×200 | 1550ms | 1729ms | 1864ms |

数据导入页与 AI 旧地址同模板、同查询，50 并发下 P95 559ms，0 错误；
划线页 P95 339ms。考试详情页本身较重（P95 1.7s），但不是本次改动，
且真实节奏下单请求 <60ms（见 §四）。

## 四、单请求基线与瓶颈

单线程连续请求（预热后取 3 次）：

| 端点 | 单请求 |
|---|---|
| `/dashboard/` | 28~52ms |
| `/assignments/manage` | 9~26ms |
| `/rooms/report` | 41~156ms |
| `/grades/print-summary?exam=34` | 5~62ms |
| `/grades/exams/34/import` | 14~30ms |
| `/grades/exams/34/bands` | 6~26ms |

结论：慢是**并发排队**，不是单条 SQL/模板慢。极限档最慢的页面是
`/dashboard/`（P50 1585ms）、`/assignments/manage`（1395ms）、
`/rooms/report`（1115ms），均在成绩模块之外；数据导入/划线页不在慢榜前列。

## 五、服务端指标与建议

极限档（97 rps）服务端日志：队列告警 10674 次，队列峰值 82，
`database is locked` **0**，Traceback 0，500 0。
瓶颈是 16 线程排队，不是锁。

建议（按性价比，需用户拍板）：

1. 生产开 WAL：`STULINK_ENABLE_WAL=1`（`history.db` 保持非 WAL），
   消除极端峰值下偶发锁争用。
2. 线程数与连接池同步提到 32/32（必须同量级），降低队列深度。
3. `/assignments/manage` 的 2000+ 元素 `IN` 改 Python 集合差（10-17 已建议）。
4. 真实使用当前已达标，以上只在"全校集中操作/极端峰值"时才有意义。
