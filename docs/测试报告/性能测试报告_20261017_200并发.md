# 性能压测报告 · 200 并发（2026-10-17）

> 目的：用户问「200 并发能不能撑得住」。本次在**真实数据副本 + 生产同规格**（waitress 16 线程、
> SQLite 多库、**未开 WAL**＝默认配置）上做多角色混合压测，量化真实使用与极限负载两条线。
> 环境：沙箱 `%TEMP%\stulink_sbx_a4`（端口 5099，16 线程），数据 2114 学生 / 31 场考试 / 102947 条成绩。
> 工具：`tests/_archive/qa_20261015/load_200.py`（probe / run / stair），结果 JSON 在 `out/`。

## 一、结论先说

| 场景 | 负载 | P50 | P95 | P99 | 错误 | 判定 |
|---|---|---|---|---|---|---|
| **真实使用**：200 人在线，平均 30 秒一次操作 | 5.7 req/s | 16ms | **187ms** | 542ms | **0** | ✅ **达标**（目标 P95<500ms） |
| 50 并发（每 1.5 秒一次） | 31.2 req/s | 16ms | 242ms | 490ms | 0 | ✅ 达标 |
| 100 并发 | 58.1 req/s | 27ms | 637ms | 1821ms | 5 | ⚠️ 开始退化 |
| **200 并发** | 54.5 req/s | 741ms | **3830ms** | 20084ms | **184** | ❌ 撑不住 |
| 300 并发 | 74.6 req/s | 2158ms | 3858ms | 5309ms | 29 | ❌ 撑不住 |

**一句话**：**「200 人同时在用」完全撑得住**（P95 187ms、0 错误，余量约 **10 倍**）；
但**「200 个请求同时打过来」撑不住**（P95 3.8 秒、184 个 500）。性能拐点在 **100 并发 / 约 58 QPS**。

> 注意区分：系统吞吐上限约 **55–75 QPS**，而 200 人真实使用只需 **6.7 QPS**（200 ÷ 30 秒）。

## 二、怎么测的

- **角色分布**按真实账号：班主任 145 / 任课教师 48 / 管理员 4 / 校长 2 共 199 个虚拟用户；
  同一账号可多 VU 复用（老师多设备是真实场景）。
- **页面池**先 probe 一遍（141 个候选，按角色取真实返回 200 的页面），避免把 403/404 当性能问题。
- **请求构成**：页面 60% + 重计算 API 40%；管理员/教务按 3% 概率发**幂等写**（查课标记同格覆盖），
  用于测 SQLite 写锁争用。
- **思考时间**：真实节奏 15–45 秒（平均 30 秒）；满载 0.5–2.5 秒（平均 1.5 秒）＝真实节奏的 20 倍。

## 三、瓶颈分析

压测期间服务端日志：

| 指标 | 数值 |
|---|---|
| `database is locked` | **2286 次** |
| waitress 队列深度峰值 | **83**（16 线程 → 排队 5 倍以上） |
| 队列告警次数 | 16239 |

**两个瓶颈，缺一不可**：

1. **SQLite 写锁争用**：读事务也会被写锁挡住，一旦排队，`locked` 直接抛 500。
   本次**未开 WAL**（默认配置）——2026-10-15 实测对照组：WAL 关→开，`locked` 116→0、5xx 54→0。
2. **线程数不足**：16 线程在 60+ QPS 时队列堆到 83，说明请求在排队而非在计算。
   ⚠️ 上次实测：**只加线程不加连接池会更差**（64 线程 / pool 10 → locked 2255、5xx 407），
   必须**线程数与连接池同量级**。

**另一个放大器**：压测里最慢的端点之一 `POST /assignments/manage`（宿舍分配）
带了一条 `~Student.id.in_(2000+ ids)` 的查询——2000 个占位符的巨型 IN 列表，
SQLite 解析开销大、持锁时间长，会放大上面两个瓶颈。
（同类问题 `report_service` 的 `_unassigned_stats` 上次已改成 Python 集合差，此处尚未改。）

## 四、与 2026-10-15 那次对比

| | 2026-10-15 | 2026-10-17（本次） |
|---|---|---|
| 真实节奏 P50 / P95 / P99 | 16ms / 242ms / 499ms | 16ms / **187ms** / 542ms |
| 真实节奏错误 | 0 | 0 |
| 200 满载 P50 / 错误 | 1s+ / 54 | 741ms / 184 |

**真实使用性能没有退化**（P95 反而略好），说明最近的计算逻辑改动（分组合拆行、加权均分、
逐生取线）对真实使用场景没有可感知影响。200 满载下的 500 数比上次多，
与「未开 WAL + 本次写比例 3%」有关，不是计算逻辑引入的。

## 五、建议（按性价比排序）

| # | 措施 | 预期 |
|---|---|---|
| 1 | 生产开 WAL：`STULINK_ENABLE_WAL=1`（`history.db` 必须保持非 WAL，alumni 只读挂载） | 消除 `database is locked`，5xx 基本归零 |
| 2 | 线程数与连接池同步提到 32/32（**必须同量级**） | 队列深度下降，吞吐上限上移 |
| 3 | 把 `assignments.py` 的 `~Student.id.in_(2000+ ids)` 改成 Python 集合差（同 `_unassigned_stats` 的改法） | 该端点 P95 从秒级降到百毫秒级 |
| 4 | 对 `/grades/ai/prompt/options`、`/workbench/` 这类静态选项加 60s 缓存 | 减少 40% API 里的重复计算 |

**是否要做 1–4 需要用户拍板**：当前真实使用已达标（余量 10 倍），
上述优化只在「极端峰值/全校集中操作」时才有意义。
