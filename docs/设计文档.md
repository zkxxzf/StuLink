# StuLink — 智联校园学生管理系统 · 设计文档

> 版本：v1.9.2（2026-09-16）
> 本文档为**总纲**：描述项目定位、核心设计理念、模块划分与数据库架构。
> 各模块的独立设计文档见「第 6 节 · 模块设计文档规范」，后续逐步补齐。

## 1. 项目概述

**StuLink（智联校园学生管理系统）** 是一套面向中学的综合学生管理平台，采用双站点架构：在校生管理系统（主应用 :5000）和往届生查询系统（独立应用 :5001）。基于 Python Flask 构建，多文件 SQLite 分库架构，支持 Docker Compose / 阿里云 ECS / NAS / Windows 本地部署。

## 2. 核心设计理念

### 2.1 模块独立，数据库隔离（一模块一库）

每个功能模块拥有**独立的数据库文件**，模块之间的数据物理隔离：

- 单模块的库文件损坏、被锁定、或结构演进，不影响其他模块；
- 每个库可独立备份、迁移与运维；
- 新模块上线只需增加一个 bind 与模型文件，不触碰既有模块。

### 2.2 松耦合数据关联（快照关联，按需读写）

模块间需要数据互通时（例如成绩模块需要学生姓名、教师工作台需要任课映射），遵循：

- **不在数据库层建立跨库外键**，跨库一律使用"快照字段"关联：
  - 学生：`student_no`（学号，全局唯一、不可变）
  - 教师/用户：`user_id`（users.id）或 `teacher_uid`（教师唯一编号）
- 允许跨模块**只读读取**对方数据（如画像模块按学号汇聚成绩/积分）；
- 读取方对来源模块的异常自行降级（读不到数据仅该功能展示受限，不影响本模块运行）。

### 2.3 故障隔离（系统管理为根基，不可被拖垮）

- **系统管理模块是项目基础**，承载底层数据（用户、学生基础信息、字典、权限组、班型、年级设置），所有模块的权限与身份都源于它；
- 应用启动时**逐库建表，单库失败仅告警不阻塞启动**（`app/__init__.py` 的 fault-isolation 建表循环）：任何业务模块库异常时，登录、系统管理等基础功能保持可用；
- 配置 `pool_pre_ping=True`，连接异常自动重建；
- 系统管理模块代码**零跨业务模块依赖**（已核查：不 import 任何 grades/points/academic/dormitory 的模型或服务）。

### 2.4 统一权限体系

- 权限通过**权限组**统一管控（`permission_groups.menu_keys`），路由用 `@perm_required('key')` 强制校验；
- 数据范围（全校/年级/班级）由 `scope_type` 控制，服务端强制过滤；
- 新模块上线：权限种子加入管理员组 + 提供存量环境补丁脚本（`scripts/add_*_perm.py`）。

## 5. 数据库设计

### 5.1 数据库清单（一模块一库）

| 数据库文件 | SQLAlchemy Bind | 归属模块 | 主要内容 |
|-----------|----------------|---------|---------|
| `data/system.db` | default（None） | 系统管理（**根基库**） | users、students、dict_categories/dict_items、permission_groups、class_profiles/class_subjects、grade_settings、user_class_links、system_settings、operation_logs |
| `data/dormitory.db` | `dormitory` | 宿舍管理 | rooms、bed_assignments、student_accommodation |
| `data/history.db` | `history` | 往届/历史 | assignment_history、graduated_students/graduated_rooms/graduated_beds、student_change_log |
| `data/grades.db` | `grades` | 成绩管理 | exams、exam_scores、exam_bands、band_templates、teacher_subject_links、ai_keys/ai_global_keys/ai_reports/ai_chat_messages、certificates/cert_signing_keys、exam_affairs/affair_rooms/affair_students/affair_room_libs |
| `data/points.db` | `points` | 积分管理 | point_records |
| `data/academic.db` | `academic` | 教务管理 | teachers、timetables/timetable_entries、inspection_records、teacher_achievements |
| `data/portrait.db` | `portrait` | 学生画像（占位） | student_profiles（占位表，字段预留） |

### 5.2 跨模块数据关联（快照关联，无跨库外键）

| 来源模块 | 目标模块 | 关联字段 | 方向 | 说明 |
|---------|---------|---------|------|------|
| 各模块 | system（学生） | `student_no`（学号） | 只读 | 学生基础信息唯一来源；学号 UNIQUE 不可变 |
| grades / academic | system（用户） | `user_id`（users.id） | 只读 | 任课映射（teacher_subject_links）、教师名单（teachers.user_id）均通过它打通 |
| points / grades | system（学生） | 学号快照 | 只读 | 点记录、成绩记录均以学号快照独立存储 |
| portrait（规划） | grades / points / dormitory | 学号快照 | 只读 | 画像按学号从各模块汇聚，不反向写入 |
| academic（教师） | system（账号） | `user_id` + `teacher_uid` | 双向维护 | 导入时自动匹配/建号（复用 grades 的 user_account 服务） |

**原则**：任何模块的数据写入只发生在自己的库；跨库读取由读取方自行容错。

### 5.3 故障隔离机制（系统性保障）

| 机制 | 实现位置 | 效果 |
|------|---------|------|
| 逐库建表容错 | `app/__init__.py` create_app | 单库损坏/锁定仅告警，应用正常启动，系统管理可用 |
| 连接自愈 | `SQLALCHEMY_ENGINE_OPTIONS.pool_pre_ping` | 连接失效自动重建 |
| 无跨库事务 | 架构约束 | 任一库的写入失败不会回滚/阻塞其他库 |
| 根基库零依赖 | 代码核查结论 | system 模块不 import 任何业务模块，业务模块崩溃不传染 |
| 密钥独立 | `data/.secret_key`、`data/.encryption_key` | 会话与加密密钥随数据目录备份，与库解耦 |

## 7. 安全设计

- **认证**：Flask-Login 会话；登录频率限制（每 IP 60 秒最多 10 次）；SECRET_KEY 持久化于 `data/.secret_key`
- **权限**：权限组统一管控（`@perm_required`）+ 数据范围过滤（scope_type：school/grade/class）
- **CSRF**：Flask-WTF 全局启用，AJAX 通过全局 `$.ajaxSetup` 注入 `X-CSRFToken`
- **敏感数据加密**：
  - 学生/教师身份证号：AES-256-CBC 确定性加密（支持等值查询），密钥 `data/.encryption_key`
  - AI API Key：随机 IV 加密存储
  - 成绩证明快照：v1.12.5 起整体 AES 加密（`enc::` 前缀），签名绑定明文，旧防伪码兼容
- **输出安全**：Jinja2 自动转义；`nl2br` 安全过滤器；前端渲染统一 `textContent`/`esc()`
- **公开端点**：成绩证明核验页带 IP 限流，仅展示脱敏信息（隐藏学籍号、脱敏身份证）

```
data/
├── system.db          ← 根基库（用户/学生/字典/权限/设置）
├── dormitory.db       ← 宿舍库
├── history.db         ← 历史库（往届数据）

├── points.db          ← 积分库
├── academic.db        ← 教务库
├── portrait.db        ← 画像库（占位）
├── .secret_key        ← Flask 会话密钥（必须备份）
├── .encryption_key    ← 加密密钥（必须备份，丢失则加密数据不可解）
└── backups/           ← 毕业操作与迁移的自动备份
```

**备份策略**：整目录备份（含两个密钥文件）；单个模块库可独立备份/迁移。

## 9. 部署架构

- **Docker 全镜像打包**：应用代码打入镜像，部署仅需镜像 tar + docker-compose.yml（数据目录 `./stulink-data:/app/data` 挂载持久化）；
- **轻量更新**：日常更新仅替换容器内代码（docker cp + restart），不重建容器；含数据库结构变更的版本需执行对应迁移脚本（新库/新表由启动时逐库建表自动创建）；
- **运行服务器**：Waitress（单 worker，SQLite 文件锁约束）；
- **往届生查询系统**：独立应用 :5001，只读访问 history.db。
