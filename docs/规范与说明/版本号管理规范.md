# StuLink 版本号管理规范

> 定稿日期：2026-10-12（自 1.19.47.8 起施行）
> 执行脚本：`scripts/bump_version.py`（四条硬规则由脚本强制校验，违反即中止）

## 一、版本号结构（四段）

```
主 . 次 . zk . sakay
 1 . 19 . 47 . 8
 │    │     │     └─ ④ sakay：本分支作者（sakaay）的改动计数 —— **每次改动及时 +1**
 │    │     └─────── ③ zk   ：主线维护者 zkxxzf 的改动计数 —— **与我们无关，不得改动**
 │    └───────────── ② 次   ：系统版本 · 里程碑 —— 发布里程碑时 +1
 └───────────────── ① 主   ：系统版本 · 里程碑 —— 大版本时才 +1
```

| 位 | 名称 | 归属 | 何时 +1 |
|---|---|---|---|
| ① | 主版本 | 系统（里程碑） | 架构级换代 / 大版本发布 |
| ② | 次版本 | 系统（里程碑） | 阶段性功能集发布（常见里程碑） |
| ③ | zk | **zk 侧控制** | zk 作者每次改动 +1（我们不碰） |
| ④ | sakay | **本分支作者** | **本作者任何一次有效改动都要 +1** |

## 二、四条硬规则

| 编号 | 规则 | 脚本校验 |
|---|---|---|
| **R1** | **bump 时机由用户决定（2026-10-13 更新）**：改动本身**不自动 bump**；用户**主动发起提交**时才由协助者执行第四位 +1 | 用户说"提交 / 推送"时：先 `bump_version sakay` 再 commit |
| **R2** | **第三段不动**：第三位归 zk 侧，本作者**任何模式（含 `set`）都不得改动** | `set` / `sakay` / `milestone` 检测到第三位变化即中止 |
| **R3** | **里程碑不重置**：升级前两位时，后两位**必须完全保留** —— 既不归零，也不顺手 +1 | `milestone` / `major` 强制后两位相等 |
| **R4** | **后两位只增不减**：`zk.sakay` 永不归零、永不回退 | 任何模式（含 `set`，需 `--force` 才破例） |

> 破例：确需回退或跨越时加 `--force`，并在提交说明中写明原因（`--force` 会打印忽略校验的痕迹）。

## 三、日常操作

```powershell
# 0. 该不该 bump？（对比上次版本号提交以来的改动）
py -3.12 -m scripts.bump_version status

# 1. 本作者每次改动（唯一日常命令）
py -3.12 -m scripts.bump_version sakay

# 2. 先看看会改哪些文件（练手/排查时用）
py -3.12 -m scripts.bump_version sakay --dry

# 3. 需要与其他改动合并成一个提交时（写盘不自动提交）
py -3.12 -m scripts.bump_version sakay --no-commit

# 4. 发里程碑（后两位原样保留）
py -3.12 -m scripts.bump_version milestone
git tag -a v1.20.47.9 -m "milestone: v1.20.47.9" && git push origin v1.20.47.9

# 5. 定期体检
py -3.12 -m scripts.bump_version check
```

### 什么时候 bump（R1 的落地口径，2026-10-13 更新）

**由用户主动发起**：改代码 / 改文档本身都**不 bump**；用户明确说"提交 / 推送 / 更新版本"时，
协助者才执行 `bump_version sakay` 并随提交一起 commit。日常改动后只改代码、不动版本号。

## 四、脚本自动处理 / 不处理清单

**会替换**（形如 `v1.19.49.49` 的引用，`.py/.html/.js/.css/.md/.txt/.yml`）：

- `config.py` 首行、`app/__init__.py`、各模块头部注释、模板、JS、所有 `.md` 文档。

**不会替换**（需人工同步）：

| 项 | 原因 | 怎么办 |
|---|---|---|
| `README.md` 的版本徽章 `badge/version-1.19.47.9-` | 无 `v` 前缀 | `check` 会报错提示，手工改 |
| `scripts/migrate/migrate_*.py`（迁移脚本） | 迁移脚本记录的是当时的版本，改了失真 | 保持不动 |
| `data/`、`docs/聊天总结/`（2026-10-13 起；脚本按目录名 `聊天总结` 跳过，与层级无关）、`.git/`、`node_modules` 等 | 目录级跳过 | 保持不动 |
| `.min.js` / `.min.css`（jquery、bootstrap） | 第三方库自带版本号 | 已按文件后缀排除 |
| **历史里程碑记录**（如"v1.19.47.6 新增"） | bump 会把"上一版本"的历史记录一并改成新版本 | bump 后跑 `check` 看"上一版本残留"清单，逐份确认是否回改 |

> 历史回改的现成做法：`bump` 后对照 `check` 的"上一版本残留"清单，把属于**里程碑描述**的那一版改回原值
> （参考 `tests/qa_20261012/fix_hist_version_refs.py`：按文件+行号精确回改，保留 BOM / CRLF）。
> **预防写法**：文档里描述历史版本时**不带 `v` 前缀**（如 `1.19.47.6 新增`），bump 就不会误改。

## 五、check 体检项说明

| 编号 | 检查项 | 输出含义 |
|---|---|---|
| 1 | 历史单调性 | 从 git 提取历次"版本号升级"提交，逐次套 R2/R3/R4；<br>规则生效起点（`1.19.47.8`）之前的违例标为 `[历史]` 仅供参考，之后标 `[错误]` |
| 2 | 引用超前 | 出现比当前还新的版本引用（多为手改过头） |
| 3 | 上一版本残留 | 仍写着上一版本的位置 —— 通常是历史里程碑记录，人工确认 |
| 4 | README 徽章 | 无 `v` 前缀的徽章是否与当前一致 |

## 六、里程碑发布流程

1. `py -3.12 -m scripts.bump_version status` 确认无遗漏改动
2. `py -3.12 -m scripts.bump_version milestone`（第二段 +1；**后两位自动保留**）
3. 同步 `README.md` 徽章（无前缀，人工）
4. **在 `docs/版本历史/` 补版本条目**（复制 `_模板.md`；7 项必填：版本号与日期 / 一句话概述 /
   改动清单六类 / 验证记录 / 影响与风险 / 回滚方式 / 待办与遗留），
   并在 `docs/版本历史/版本索引.md` **加一行** —— 该目录已在 `SKIP_DIRS` 内，bump 不会改写它
5. `push` + 打 tag：`git tag -a v<X.Y.Z.W> -m "milestone: v<X.Y.Z.W>"`
6. 更新 `docs/规范与说明/用户文档.md` 的"版本记录"章节

> **本规范管版本号（叫什么、怎么加）；`docs/版本历史/README.md` 管版本内容
> （改了什么、为什么、怎么验、怎么退）。两者都要做。**
