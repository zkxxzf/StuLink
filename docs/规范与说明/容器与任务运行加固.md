## 2. 仍未做（需要运维/架构决策，不在本批自动执行）

1. **非 root 运行**：容器当前仍以 root 启动。直接改 `USER` 会因 NAS 上
   `stulink-data` 的宿主 UID 不匹配而写库失败。正确顺序：
   ```bash
   # 宿主机
   chown -R 1000:1000 /volume1/docker/stulink-data
   # compose 里给 stulink/alumni/mcp 加
   user: "1000:1000"
   ```
   先在测试容器验证上传/备份/日志写入，再切生产。
2. **只读根文件系统**：`read_only: true` 会阻止 `app/static/uploads` 写入；
   需先把上传目录改成具名卷或 `data/uploads`，再开只读 + `tmpfs: /tmp`。
3. **镜像 digest 固定**：当前 compose 用 `stulink:v1.7.0` 等 tag；发布流程应改为
   `image: <repo>@sha256:<digest>`，并在更新单里记录 digest。
4. **持久任务队列**：当前只是“进程内有界并发”，不是队列；进程重启仍会把
   `running` 任务标为 `interrupted`。要跨重启续跑，需引入 Redis/RQ/Celery 或
   DB 队列 + 单独 worker，属于架构升级，不在本批。
5. **`data/` 移出同步盘**：见 §3，必须停机窗口操作。

## 3. `data/` 移出同步盘（运维 SOP，未执行）

目标：SQLite、密钥、备份、上传不再落在 OneDrive/坚果云等同步目录。

1. 停容器：`docker compose -f deploy/docker-compose.yml stop stulink alumni mcp`
2. 全量复制（不要移动，保留回滚）：
   ```bash
   rsync -a --delete /volume1/docker/stulink-data/ /volume1/stulink-data/
   ```
3. 改 compose 三个服务的卷：
   ```yaml
   volumes:
     - /volume1/stulink-data:/app/data
   ```
4. 启动并验证：`/health` 200、登录、成绩查询、备份脚本、MCP 读一条。
5. 观察 1 周无异常后，再删除旧同步目录；保留至少一份离线备份。
6. 回滚：停容器，把卷路径改回 `./stulink-data`，启动。

注意：
- 不要在容器运行时直接 `mv` 同步盘目录；SQLite 的 `-wal/-shm` 会不一致。
- 迁移后同步盘里可能仍有历史 `.bak`/密钥副本，按 H-07/H-08 的清理脚本单独处理。
- 密钥文件建议同时用 `STULINK_SECRET_KEY_FILE` / `STULINK_ENCRYPTION_KEY_FILE`
  指向新目录，避免代码回退时又读到旧路径。
