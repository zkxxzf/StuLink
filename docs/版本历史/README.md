# 版本历史（StuLink）

> 本目录是**版本历史的唯一真值**：记录「哪个版本、什么时候、做了什么、为什么、怎么验证、怎么回滚」。
> 版本号规则见 [`docs/规范与说明/版本号管理规范.md`](../规范与说明/版本号管理规范.md)；本目录管**内容**。

## 一、什么时候必须写

| 场景 | 必须写 |
|---|---|
| 用户说「提交 / 推送 / 更新版本」并 bump 了版本号 | ✅ 同批次内完成，不许拖到下次 |
| 一次有效改动跨多个功能点（>3 个文件或 1 个完整功能面） | ✅ 哪怕还没提交，先记一条「待提交」 |
| 审计/修复批次、脚本写库、数据库迁移 | ✅ 必须写清「怎么验证」与「怎么回滚」 |
| 只改文档措辞、单条注释 | ❌ |
| 纯查询、只读审计（没改代码） | ❌ 审计结论写进对应审计报告即可 |

> 判定口径一句话：**别人拿到这个版本号，能不能查清「改了什么、为什么改、怎么验、怎么退」？**
> 答不上来 → 就得写。

## 二、命名规范

```
docs/版本历史/YYYY-MM-DD_vX.Y.Z.W_主题.md
例：2026-10-16_v1.19.49.34_全项目审计第七与八轮.md
```

- 日期用**改动完成日**（不是启动日）。
- 版本号写 **bump 之后**的号；尚未 bump 先写 `待提交`。
- 主题短、能一眼区分（别写 `misc`、`update`）。
- 一次 bump 一个文件；跨多天或多次 bump，按版本号拆多个文件。

## 三、条目必填字段（缺一项即没写完）

1. **版本号与日期** —— 与 `config.py` 首行一致。
2. **一句话概述** —— 这一版最核心的一件事。
3. **改动清单** —— 分「新增 / 修复 / 优化 / 重构 / 文档 / 脚本」六类，每条说清「改了什么 → 为什么」。
4. **验证记录** —— 跑了哪些回归与测试、数字、证据脚本路径。
5. **影响与风险** —— 副作用、影响模块、要不要重启容器、有无数据库迁移。
6. **回滚方式** —— `git revert <commit>` / 关 flag / 回滚脚本 / 恢复备份。
7. **待办与遗留** —— 这一版没做完的、留给下一版的。

模板见 [`_模板.md`](./_模板.md)，复制后改标题即可。

## 四、索引

[`版本索引.md`](./版本索引.md) 按版本号倒序，每行给「版本 · 日期 · 一句话 · 链接」。
新增条目后**必须同步加一行**（最容易漏的一步）。

## 五、两条硬约束

1. **本目录不会被 `bump_version.py` 改写**（已加入其 `SKIP_DIRS`）——
   历史里的版本号必须保持原样，改了历史等于伪造历史。
2. **与 `docs/聊天总结/` 的分工**：聊天总结写「这轮做了什么、怎么沟通」（过程）；
   版本历史写「这一版是什么、能追溯什么」（结果）。两者都要有，不要互相替代。
