# 宿舍分配算法设计规范

> **版本**: v20260805  
> **最后更新**: 2026-08-02  
> **核心策略**: 平滑动态贪心 —— 全局压力等级制，优先保持每间宿舍人数 ≤6 人，床位不足时整体升档至 7-8 人间；合班宿舍人数上限与普通房间一致，跟随全局宽松程度，压力均匀分布
> **基于**: 高中宿舍分配算法说明文档（v20260805）+ 本项目（StuLink）数据模型与接口适配

---

## 〇、核心关键（速览）

1. **软上限优先**：8人间默认只住 6 人，只有床位整体不足时才升到 7/8 人
2. **全局压力等级 L**：从 6 开始递增，取第一个满足 `Σ min(L, 房间容量) ≥ 总人数` 的等级（6/7/8）——所有房间（含合班房）统一按 `min(L, 容量)` 入住，压力均匀分布，不会出现"普通房6人、合班房8人"的失衡
3. **自动三档模式**：L=6 → 宽松；L=7/8 → 紧张。无需人工调参
4. **合班被动触发**：班级收尾剩余不足当前上限（1~5人）时，与下一班（同性别 + 同年级 + 同班型）合并；**合班房人数上限 = min(L, 容量)，与普通房完全一致**
5. **S型连续**：房间按"偶数层正向、奇数层反向"序列化，班级在全局序列上顺序切段，同一班宿舍物理相邻
6. **高年级优先低楼层**：班级按（年级、班型、班号）排序，高年级先分配 → 先占低楼层
7. **每班最多发起 1 次合班（被借不算发起）、每间合班 ≤2 个班、合班人数尽量 ≥4**（极端可少）
8. **全量校验**：分配结束必须满足 Σ实际入住 = Σ总人数，否则报错/提示增选宿舍
9. 本算法只计算“班级 + 房间 + 预计人数”，不涉及具体床位，与现有床位分配完全解耦
10. **合班宿舍调整（后处理优化）**：主分配结束后自动分解链式合班（如 01+02、02+03），中间班可独立成房且两端班可重组时减少合班宿舍数量，不影响主算法结果

## 一、约束条件（必须完全满足）

| 约束 | 规则 |
|------|------|
| 性别分开 | 男女独立分配，算法逻辑相同，互不影响；房间 `gender` 字段严格隔离（男/女/不限） |
| 合班性别 | 仅同性别 |
| 合班年级 | 仅同年级（`grade` 完全一致） |
| 合班班型 | 仅同班型（`ClassProfile.class_type`：强基班/卓越班；无记录 → `default`，自成一组） |
| 合班班级数 | 每间合班宿舍最多 2 个班 |
| 合班人数 | 合班宿舍人数尽量 ≥4 人（极端情况可接受更少）；**上限 = min(L, 容量)，与普通房一致，跟随全局宽松程度** |
| 合班时机 | 只发生在班级收尾且剩余人数 < 当前房间上限（1~5人）时 |
| 合班次数 | 每班最多发起 1 次合班（被借不算发起）；**不可限制为"参与1次"（发起+被借都算），否则收尾班只能独占小房间、浪费床位，实测男女均分配失败** |
| 房间容量 | 6人间/8人间，物理床位数即人数上限（`capacity`） |
| 班级连续 | 同一班宿舍在 S 型序列上物理相邻；系统缺号时跳过缺失房间，相邻房仍视为连续；跨楼层按 S 型连接（如 2楼 219→220→221 尽头后接 3楼 323→322→321） |
| 年级楼层 | 高年级优先低楼层（班级排序 + 房间楼层升序实现） |
| 总床位 | 每性别：Σ物理床位 ≥ 需入住总人数，否则直接报错 |
| 管理偏好 | 尽量每间住 ≤6 人、不合班；只有装不下时才整体升档，收尾被动合班 |

## 二、核心机制详解

### 2.1 全局压力等级 L

```
L = 最小的等级（从 6 开始递增，最大 8），使得：
    Σ min(L, 每间房间容量) ≥ 该性别需入住总人数
```

- L=6：所有房间按 6 人入住即可装下 → **宽松模式**（8人间住6人、6人间住6人）
- L=7：按 6 人装不下，按 7 人可以 → **紧张模式**（8人间住7人、6人间住6人）
- L=8：按 7 人仍装不下，按 8 人物理床位可装 → **极限模式**（8人间住8人、6人间住6人）
- 若 `Σ 物理容量 < 总人数`（L=8 也不行）→ **报错**，提示增选宿舍

**为什么是"全局"而不是"逐间前瞻"**：
逐间前瞻容易产生"前面房间住6人、合班房却单独升到8人"的失衡；全局等级制让**所有房间（含合班房）统一升档**——普通房住7时合班房也最多7，普通房住8时合班房才允许8。学生住得均衡、住得好。

**房间数兜底（分配失败自动升档重试）**：
L 只保证"床位可行"（Σ min(L, 容量) ≥ 总人数）；但班级收尾的独占小房间会额外消耗房间数，极端时可能出现"床位够、房间不够"（例如女生 69 间时 L=7 床位可行 445≥444，但收尾独占挤占房间数导致 L=7 分配失败）。此时按 **L → L+1 → … → 8** 自动升档重试——每间住更多人、消耗房间更少：
- 升档后成功 → 以实际成功等级为准（页面展示升档后的 L 与模式）
- L=8 仍失败 → 报错"房间不足，请增选宿舍"（物理不可行）

该机制保证：**多选房间只会让 L 更低/更宽裕，不会出现"多选反而失败"**。

### 2.2 房间入住上限

```
limit = min(L, 房间容量)
```

- 8人间：L=6 → 6人；L=7 → 7人；L=8 → 8人
- 6人间：永远 6 人（软硬上限相同）

### 2.3 分配粒度

每间房尽量住满 `limit`；班级收尾（剩余 < limit）时与下一班合班，合班房也住满 `limit`（借人填满），仅末班或班型边界才产生低入住房间。

## 三、预处理

### 3.1 班级排序

```
对每个性别独立的班级列表排序：
key = (年级数字升序, 班型, 班号升序)
```

- **年级数字**：`2023级 → 2023`（`_extract_grade_year`）。数字小 = 高年级（如 2023级=高三、2024级=高二），排前面 → 先分配 → 先占低楼层
- **班型**：强基班 / 卓越班 / default。同班型相邻 → 收尾合班时"下一班"天然满足班型条件，最大化合班可行性
- **班号**：`01班 → 02班`（`_extract_class_number`），同年级同班型内按班号升序

### 3.2 房间 S 型序列化

```
sortRooms(rooms):
  1. 按楼栋分组（多栋楼时每栋独立 S 型，栋间按楼栋名顺序连接）
  2. 每栋内按楼层分组，楼层内按房间号升序（房间号数字比较，缺号自然跳过）
  3. 楼层号偶数的楼层 → 正向连接
     楼层号奇数的楼层 → 反向连接
  4. 楼层升序依次连接 → 全局有序列表
```

示例：

```
2楼（偶数，正向）:  201 → 202 → … → 212
3楼（奇数，反向）:  323 → 322 → … → 301
S型序列: 201, 202, …, 212, 323, 322, …, 301
```

### 3.3 容量评估与等级判定

按 2.1 节公式计算全局压力等级 L（记为 L0，初始等级）：
- 物理床位不足 → 直接报错退出
- L0=6 → 宽松模式；L0=7/8 → 紧张模式；写入日志
- **注意**：L0 仅保证床位可行；实际分配若"房间不足"会自动升档重试（见 4.1），最终等级可能高于 L0

## 四、核心分配流程（伪代码）

### 4.1 单性别主流程（含失败自动升档重试）

```
function allocateOneGender(rooms, classes, L0):
    # rooms:   已按 S 型排序的房间数组（空闲房，occupied 初始 0）
    # classes: 已按 (年级数字, 班型, 班号) 排序的班级数组
    # L0:      2.1 节计算的最低可行等级（6/7/8）；物理床位不足已在外层报错退出

    # 升档重试：L 只保证床位可行；若分配时"房间不足"（收尾独占挤占房间数），
    # 依次尝试 L, L+1, ..., 8 —— 每间住更多人、房间消耗更少
    for L = L0 to 8:
        result = allocateOnce(rooms, classes, L)   # 用等级 L 完整跑一趟（主流程见下）
        if result.success:
            return {level: L, mode, allocations, room_details}
        # 记录日志：L=7 房间不足（收尾班级占房过多），自动升档 L=8 重试

    报错: L=8 仍无法分配 → "房间不足，请增选宿舍"

function allocateOnce(rooms, classes, L):
    # L: 当前尝试等级（6/7/8），房间入住上限 limit = min(L, r.capacity)

    room_idx = 0
    has_merged = False
    merge_prev_share = 0          # 合班房中"前一个班"的份额，用于下一班记录 borrowed
    class_rem = {c.key: c.count}  # 各班剩余未分配人数
    allocations = {c.key: []}     # 各班分配结果: [(room_idx, count), ...]
    room_details = {}             # 每间房实际班级分布: {room_idx: [(class_key, count), ...]}
    initiated = {}                # 发起过合班的班级（被借不算），每班最多发起 1 次

    for i = 0 to classes.length - 1:
        cur = classes[i]
        rem = class_rem[cur.key]
        if rem == 0: continue

        # ---- 处理上一班遗留的合班房 ----
        if has_merged:
            r = rooms[room_idx]
            borrowed = r.occupied - merge_prev_share   # 下一班在合班房中的份额
            allocations[cur.key].append((room_idx, borrowed))
            room_details[room_idx].append((cur.key, borrowed))
            has_merged = False
            room_idx += 1

        # ---- 分配当前班 ----
        while rem > 0:
            # 跳过已满房间
            while room_idx < rooms.length and rooms[room_idx].occupied >= rooms[room_idx].capacity:
                room_idx += 1
            if room_idx >= rooms.length:
                报错: 房间不足（物理床位虽有富余，但收尾独占导致房间数不够，提示增选宿舍）

            r = rooms[room_idx]
            limit = min(L, r.capacity)                 # 本间入住上限（全局等级制）

            if rem >= limit:
                # ===== 正常填充：住满本间上限 =====
                occ = limit
                r.occupied = occ
                allocations[cur.key].append((room_idx, occ))
                room_details[room_idx].append((cur.key, occ))
                rem -= occ
                room_idx += 1

            else:
                # ===== 收尾: 0 < rem < limit（1~5人）=====
                if i == classes.length - 1:
                    # 最后一班 → 独占小房间
                    r.occupied = rem
                    allocations[cur.key].append((room_idx, rem))
                    room_details[room_idx].append((cur.key, rem))
                    rem = 0
                    room_idx += 1
                else:
                    nxt = classes[i + 1]
                    next_rem = class_rem[nxt.key]

                    # 合班条件：下一班有剩余 + 同班型 + 本班未发起过合班（被借不算发起；同年级由排序保证）
                    if next_rem <= 0 or nxt.class_type != cur.class_type or cur.key in initiated:
                        # 班型边界/下一班已空/本班已发起过合班 → 独占小房间
                        r.occupied = rem
                        allocations[cur.key].append((room_idx, rem))
                        room_details[room_idx].append((cur.key, rem))
                        rem = 0
                        room_idx += 1
                    else:
                        # ===== 合班：目标 = 本间上限（与普通房一致）=====
                        max_possible = min(limit, rem + next_rem)   # 借人填满上限，但不超过下一班剩余
                        occ = max_possible
                        borrowed = occ - rem                        # 从下一班借用的人数

                        r.occupied = occ
                        allocations[cur.key].append((room_idx, rem))   # 当前班只记自己的份额
                        room_details[room_idx].append((cur.key, rem))   # 精确份额，供 combined_details 使用
                        class_rem[nxt.key] -= borrowed
                        initiated[cur.key] = True                 # 本班已发起合班，后续收尾只能独占
                        has_merged = True
                        merge_prev_share = rem
                        rem = 0
                        # room_idx 不递增 → 下一班继续使用这间合班房
                        break

    # ---- 最终校验 ----
    if Σ(allocations 所有人) != Σ(各班总人数): 记录警告/报错

    return { allocations, room_details }
```

> 注：全局等级 L 只保证床位可行（Σ min(L, 容量) ≥ 总人数）；分配时若"房间不足"（多为收尾独占小房间过多挤占房间数，如女生 69 间 L=7 失败），自动升档重试（L+1…8）——升一档通常即成功（每间住更多人、房间消耗更少）；L=8 仍失败才报错提示增选宿舍。

## 五、合班机制详解

### 5.1 触发条件（同时满足）

| 条件 | 说明 |
|------|------|
| 班级收尾 | 当前班剩余 rem ∈ [1, limit-1]，即 1~5 人（limit 随 L 变化） |
| 非末班 | 序列中还有下一个班（`i < classes.length - 1`） |
| 下一班有剩余 | `class_rem[nxt] > 0` |
| 同班型 | `nxt.class_type == cur.class_type`（同年级、同性别由分组与排序保证） |
| 本班未发起过合班 | `cur.key not in initiated`（被借不算发起；**被借过的班仍可发起合班**） |

任一不满足 → 当前班独占小房间（1~5人，接受小房间）。

### 5.2 合班房人数计算

```
limit       = min(L, 房间容量)                  # 合班房上限 = 普通房上限，跟随全局宽松度
max_possible = min(limit, rem + next_rem)       # 借人填满上限，但不超过下一班剩余
occ         = max_possible                     # 合班房实际入住
borrowed    = occ - rem                        # 从下一班借用的人数
```

- **宽松模式（L=6）**：合班房上限 6 → 普通房住6时合班房最多6
- **紧张模式（L=7/8）**：合班房上限 7/8 → 普通房住7/8时合班房才允许7/8
- 下一班人数不足时：`occ = rem + next_rem`（借空下一班，合班房可少于上限）
- 合班房人数尽量 ≥4；极端情况（下一班只剩1人且rem很小）可少于4

### 5.3 份额记录（与 combined_details 精确对应）

合班房每班人数必须精确记录：

```
room_details[合班房] = [
    (当前班.key, rem),        # 当前班全部剩余
    (下一班.key, borrowed)    # 下一班借用份额（轮到下一班时补记）
]
```

> 这是本算法与旧版的关键区别：旧版 stream-filling 的"边界房间"只归属主要班级，导致床位分配时次要班级学生"消失"（42人未分配问题）。新版从源头精确记录每班份额，合班房写入 `combined_details`，房间分配与床位分配天然一致。

### 5.4 继承机制

- 合班房分配后 `room_idx` **不递增**，下一班从这间合班房继续
- 轮到下一班时，先记录 `borrowed` 份额（`allocations` + `room_details`），再分配自己的剩余学生
- 下一班被完全借空（`class_rem[nxt]` 减到 0）→ 该班仅合班房一间，轮到它时记录份额后正常结束

### 5.5 连续性保证

- 合班房位于两个班宿舍的边界位置（当前班最后1间 = 下一班第1间）
- 因为班级在 S 型全局序列上顺序切段，每个班（含合班房）物理相邻

### 5.6 合班宿舍调整（后处理优化步骤）

主分配完成后追加的纯优化步骤（`_optimize_combined_rooms`），**不改变主算法的分配结果与约束**，只重组合班房的班级配对，目标：**减少合班宿舍数量**。

**问题背景（链式合班）**：班级连续收尾时可能产生链式合班：

```
合班房A(01班5人, 02班1人) → 合班房B(02班5人, 03班1人) → 合班房C(03班5人, 04班1人)
```

02班在合班房A中仅 1 人、03班在合班房B中仅 1 人——两个班都要“管理”合班宿舍，但每个班只涉及少量学生，管理成本高。

**调整规则（一次迭代）**：对每个“中间班”B（同时出现在 2 间合班房：被借房 + 发起房）：

```
条件1: B 的合班总份额 t = 被借份额 + 发起份额 ≤ 发起房上限 min(L, 容量)
       → B 可独立成 1 间房（释放 2 间合班房）
条件2: 前班份额 a + 后班份额 b ≤ 被借房上限 min(L, 容量)
       → 前班与后班可重组成 1 间合班房
两者同时满足 → 拆 2 间合班房，重组为 1 间合班房 + 1 间独立房，合班宿舍数 -1
```

迭代执行直到无中间班可调整（每轮最多 30 次，实际链长有限）。

**示例**（L=7，8人间上限7）：

```
调整前: 合班房A(01班5, 02班1)  合班房B(02班5, 03班1)  合班房C(03班5, 04班1)
调整后: 合班房A(01班5, 04班1)  02班6人独立           03班6人独立
```

合班宿舍 3 间 → 1 间（另 2 个班独立成房），房间数与总人数不变。

**约束保持（调整不会破坏）**：

| 约束 | 说明 |
|------|------|
| 同年级同班型 | 链内班级天然同班型（原合班房约束），重组不引入异班型 |
| 发起次数 ≤1 | 前班拆掉原发起房后重新发起（仍1次）；后班保持被借身份；中间班独立后不再发起 |
| 房间上限 | 重组后的 2 间房分别按各自房间上限校验（条件1/2） |
| 总人数守恒 | 仅调整班级份额归属，人数不变 |
| 房间位置不变 | 只改房间内班级分布，不移动房间，S 型连续性不变 |

**日志**：每次调整输出 `[V20260805-女优化] 合班调整: 拆01班+02班、02班+03班 → 01班+04班合班 + 02班6人独立（合班宿舍-1）`，结束时输出 `合班宿舍调整完成: 共减少 N 间合班宿舍`。

## 六、特殊边界与情况处理

| 场景 | 处理方式 |
|------|----------|
| 班级人数为 0 | 直接跳过，不分配房间 |
| 某班最后剩 1~5 人且非末班 | 与下一班合班（同班型），合班房住满上限 |
| 末班最后剩 1~5 人 | 独占房间，接受小房间 |
| 收尾但下一班班型不同 | 独占小房间（不合班） |
| 连续多个班级收尾均需合班 | 每个合班房作为相邻两班的边界，班级连续性保持；主分配后由 5.6 节优化步骤自动分解链式合班（如 01+02、02+03 → 01+03 合班 + 02 独立），减少合班宿舍 |
| 下一班被完全借空 | 该班仅有合班房一间，仍正常结束 |
| 宽松模式（L=6） | 所有房间（含合班房）≤6 人，无 7/8 人间 |
| 紧张模式（L=7/8） | 8人间整体升档为 7/8 人，合班房同步升档，压力均匀 |
| 合班宿舍人数超过 6 人 | 仅 L=7/8 时发生，与普通房一致 |
| 系统缺号（如缺 220） | 排序时自然跳过，219→221 视为连续 |
| S 型跨层连接 | 2楼 222,223 之后接 3楼 323,322,321，排序后序列相邻 |
| 分配结束仍有剩余学生 | 记录警告；若因收尾独占导致房间不够 → 报错提示增选宿舍 |
| 物理床位不足（L=8也不行） | 直接报错，提示增选宿舍 |

## 八、示例推演

### 示例A：宽松模式（L=6）

```
班级（同年级同班型）：01班15人、02班15人、03班9人、04班9人 = 48人
房间：201-209（9间8人间，Σmin(6,8)=54 ≥ 48 → L=6，limit=6）
```

| 房间 | 过程 | 结果 |
|------|------|------|
| 201 | 01班住满上限6 | 01班6 |
| 202 | 01班再住 | 01班6 |
| 203 | 01班剩3收尾 → 与02班合班（目标6） | **01班3 + 02班3** |
| 204 | 02班（借走后剩12）住 | 02班6 |
| 205 | 02班再住 | 02班6 |
| 206 | 03班（同班型）住 | 03班6 |
| 207 | 03班剩3收尾 → 与04班合班 | **03班3 + 04班3** |
| 208 | 04班（借走后剩6）住 | 04班6 |
| 209 | 空闲（宽松模式剩余房） | 空闲 |

校验：01班 6+6+3=15 ✓、02班 3+6+6=15 ✓、03班 6+3=9 ✓、04班 3+6=9 ✓。共 48 人，8 间使用，所有房间（含合班房）≤6 人。

### 示例B：紧张模式（L=8，整体升档）

```
班级：01班28人（无其他班）
房间：201-204（4间8人间，Σmin(7,8)=28 = 28 → L=7？)
```

> 修正：28人 / 4间8人间：Σmin(6,8)=24 < 28；Σmin(7,8)=28 ≥ 28 → **L=7，limit=7**（宽松优先，能7不8）。

| 房间 | 过程 | 结果 |
|------|------|------|
| 201 | 01班住满上限7 | 01班7 |
| 202 | 01班再住7 | 01班7 |
| 203 | 01班再住7 | 01班7 |
| 204 | 01班剩7收尾（=上限，正常住满） | 01班7 |

校验：7+7+7+7=28 ✓。L=7 时所有 8 人间统一住 7 人，不会出现"有的8人有的6人"。

### 示例C：合班房跟随全局等级

```
班级（同班型）：01班15人、02班12人 = 27人
房间：201-204（4间8人间，Σmin(6,8)=24 < 27；Σmin(7,8)=28 ≥ 27 → L=7，limit=7）
```

| 房间 | 过程 | 结果 |
|------|------|------|
| 201 | 01班住7 | 01班7 |
| 202 | 01班再住7 | 01班7 |
| 203 | 01班剩1收尾 → 与02班合班（目标上限7） | **01班1 + 02班6**（7人合班房） |
| 204 | 02班（剩6）住 | 02班6 |

校验：01班 7+7+1=15 ✓、02班 6+6=12 ✓。合班房上限 = 普通房上限 = 7，完全同步。

## 九、多场景模拟测试结论

> 测试时间：2026-08-02 ｜ 测试数据：2024级/2025级住校生（男486人、女444人） ｜ 方式：复用算法核心逻辑的独立脚本，只读数据库，未写入任何数据

| 场景（每性别勾选房间数） | 男生结果 | 女生结果 |
|------|----------|----------|
| 只选 2 间 | FAIL：486人 > 16床，报错"物理床位不足" | FAIL：444人 > 12床，报错"物理床位不足" |
| 只选 20 间 | FAIL：486人 > 160床 | FAIL：444人 > 134床 |
| 选 78 间 | **L=7 紧张**：486/486 全分配、16间合班（8人间合班=7人）、使用72/78间 | **L=6 宽松**：444/444 全分配、14间合班（全部6人）、使用77/78间 |
| 全选 110 间（2-6层） | L=6 宽松：486/486、14间合班、使用83/110间、空闲27间 | L=6 宽松：444/444、14间合班、使用77/110间、空闲33间 |
| 回归 66 间（2-4层） | L=8 极限：486/486、16间合班、使用64/66间、空闲2间 | L=8 极限：444/444、15间合班、使用66/66间、空闲0间 |

**测试结论：**

1. **床位不足报错清晰**：物理床位不足时直接失败并提示差额（如“486人 > 16床”），引导增选宿舍，不产生半途结果
2. **男女同批房间自动不同等级**：78间场景男 L=7、女 L=6 —— 等级按各性别独立计算、互不拖累，同时验证“合班房上限跟随全局宽松程度”（同批房间内 8 人间合班房=7人 与 全部6人 并存是正常现象）
3. **人数均衡**：每班除 1 间收尾房（合班房/独占小房）外全部住满当前上限 limit，无“有的房6人、有的房8人”的失衡
4. **合班合理**：每间合班宿舍恰好 2 个班、同年级同班型、每班最多发起 1 次合班、合班房人数 = 当前上限（78间场景 8 人间合班=7人、110间场景合班=6人）
5. **宽松优先**：L 从 6 递增取第一个满足的等级，能 6 人绝不 7 人（全选110间时男女均回到 L=6 宽松模式）

> **合班宿舍调整复测（2026-08-02 新增后处理步骤）**：以上合班间数为优化前数值。新增优化步骤后复测：用户 70 间场景（女 444 人 L=7）合班 **16 → 13 间**；全选 110 间（L=6）男 **14 → 13 间**、女 **14 → 11 间**。调整仅减少合班宿舍数量，人数、使用房间数、压力等级均不变。

## 十、前端实时拥挤提示设计

### 10.1 目标

用户在分配页第2步"选择宿舍"时，每勾选一间房，页面即时提示：以当前勾选房间分配之后会不会拥挤——全部≤6人 / 6人间合班宿舍 / 7人间合班宿舍 / 8人间住满 / 床位不足。

### 10.2 接口

扩展 `/rooms/assign-auto/room-stats`（POST，参数 `room_ids` + `selected_keys`）返回值，新增每性别压力评估：

```json
{
  "success": true,
  "male_rooms": 20, "male_beds": 160,
  "female_rooms": 20, "female_beds": 134,
  "male_pressure": {
    "ok": true, "level": 7, "mode": "紧张", "combined_rooms": 16,
    "total": 486, "beds": 160, "error": ""
  },
  "female_pressure": { "ok": true, "level": 6, "mode": "宽松", "combined_rooms": 14, "total": 444, "beds": 134, "error": "" }
}
```

- `ok=false` → 物理床位不足（`error` 含报错信息，如"486人 > 160床"）
- `level` → 全局压力等级 6/7/8；`mode` → 宽松/紧张
- `combined_rooms` → 按当前勾选房间**完整跑一遍分配**后的合班间数（算法毫秒级，见 10.4）

### 10.3 五种提示状态（男女分别显示）

| 状态 | 判定 | 提示文案示例 |
|------|------|--------------|
| 床位不足 | `ok=false` | 红色：男生床位不足（486人 > 160床），需增选宿舍 |
| 宽松无合班 | `ok && level==6 && combined_rooms==0` | 绿色：男生宽松模式：全部宿舍≤6人 |
| 宽松有合班 | `ok && level==6 && combined_rooms>0` | 绿色：男生宽松模式：全部≤6人，有合班宿舍 |
| 紧张（7人间） | `ok && level==7` | 橙色：男生紧张模式：8人间住7人，有合班宿舍≤7人 |
| 极限（8人间住满） | `ok && level==8` | 红色：男生极限模式：8人间住满8人，有合班宿舍≤8人 |

### 10.4 性能

- 算法为 O(班级数×房间数) 一趟贪心：≤40班 × 110间 ≈ 几千次操作，后端接口实测毫秒级
- 前端对勾选事件做 250ms 防抖，连续勾选只触发最后一次计算
- **结论：能实现、不会卡**

## 十一、与旧版（v7）算法的关键区别

| 特性 | 旧版（v7） | 新版（v20260805） |
|------|-----------|-------------------|

| 房间序列 | (楼栋,楼层,房号)全升序 | S型（偶数层正向、奇数层反向） |
| 班级排序 | 按班号 | (年级, 班型, 班号)，高年级优先 |
| 合班房人数记录 | 边界房间归属不清 | 每班份额精确记录（combined_details） |
| 房间浪费 | 紧张时末端集中满员 | 等级制下仅班型边界/末班小房间少量浪费 |
